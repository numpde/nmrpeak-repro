NMRPeak adoption of the shared API proxy and outbox
===================================================

Status: design based on nmr-provider-tools note 020, 30 October 2026.
This describes intended changes, not an SDK release, implementation or live
result. The shared-package owner owns both shared services and their SDK;
NMRPeak owns its provider integration and scientific and journal lifecycles.

Outcome
-------

NMRPeak uses two independently managed host services: a shared API CONNECT
proxy and a shared durable outbox, each with one socket. Provider, journal,
archive and maintenance API exchanges use the proxy. The provider hands terminal
results and their publication inputs to the outbox through the shared SDK. The
outbox uses the proxy to publish independently of the provider. NMRPeak never
starts, stops, initializes, reconfigures or removes either shared service or its
storage. Provider changes must leave the deployed proxy and its volume running.

The first joint milestone is all four providers and the outbox operating against
nmr.localhost through the one API proxy, with the replaced private API proxies
and delivery intakes retired. Count actual API proxy roles, not just containers.
Configuration replacement and service interruption are accepted, including
while delivery has pending work. An empty queue, old-configuration preservation,
parallel deployments and uninterrupted publication are not prerequisites.
Retain existing queue ownership, exact accepted commands, provider identity,
signing/TLS and uncertain-effect rules. A paused publisher caused by a bad
credential or grant must be repaired; retained bytes alone are not working delivery.

Shared contract needed by NMRPeak
---------------------------------

The SDK supplies an API client grant and an outbox intake grant. Each names an
external host-owned volume, read-only mount, socket path and supplementary access
GID. Add both groups without dropping existing grants; deduplicate equal GIDs.
Consumers do not create, relabel, initialize or remove either volume. A direct
docker run borrower must inspect the exact volume's existence before launch:
volume-nocopy alone does not stop Docker creating missing named storage.

The proxy accepts client CONNECT destinations under the host-wide allowed
authorities policy. NMRPeak signs its own API requests and verifies TLS; the proxy
gets no signing credential. Host operator configuration controls proxy connection
capacity, log level and allowed authorities live. Its separate outbox settings
control queue capacity, retry and logging live. Providers neither edit that file
nor restart the proxy to join, leave or change deployment. Actual socket names,
GIDs, SDK symbols and handoff format are shared-owner decisions; do not guess an
SDK release or carry forward the former per-binding projection interface.

The SDK handoff carries the exact terminal operation and body, Job/Attempt and
API/provider identity, and the publication API settings, issued signing
credential and optional CA material. Provider-container paths, in-memory key
objects or a pre-signed request are not sufficient outbox publication material.
The outbox durably commits result and usable inputs together before acknowledging;
it signs fresh requests and verifies TLS/receipts on publication attempts. Keep
private material out of logs, status, diagnostics and public artifacts. After an
acknowledgement the outbox owns accepted work, including after provider removal.
A lost acknowledgement leaves the producer's obligation subject to the existing
identical-replay and uncertainty rules. A replay acknowledgement must describe
the publication inputs actually retained; changed inputs cannot silently replace
the originals or be represented as stored. Acknowledgement is not API acceptance
or a guarantee against host/storage loss.

NMRPeak currently reserves up to 131072 terminal-body bytes per lane and 262144
for two lanes. Preserve those result-body budgets when credential/CA material and
encoding are added to the handoff; do not silently reduce or truncate a result.
The shared intake's present 2 MiB request ceiling must be revised as needed for
every supported provider's full terminal body plus bounded publication inputs
and encoding. Account separately for retained publication material in actual
outbox storage sizing.

No central provider registration, provider-specific delivery socket or static
list of provider bindings is required. The handoff must match the supplied
provider identity to its credential fields. The SDK's existing credential parser
checks artifact fields and the matching key pair; it does not prove API issuance
or current authorization. The API authenticates publication. The shared socket
is a trusted local submitter boundary, not per-provider authentication.

The shared intake is push-only: it accepts a
handoff and returns its durable acknowledgement or refusal. Providers cannot read
pending items, status, inventory or capacity through it. The operator's separate
inspection path does not grant that capability to provider containers. A conflict
refusal for a guessed matching identity can reveal limited existence information;
this disclosure is accepted for the controlled host. Do not claim zero metadata
leakage. Preserve per-provider and total backpressure
at the outbox; never expose retained signing or CA material in replies. Agree the
submission interface with the shared owner before implementation; no wire schema
or SDK symbol is assumed here.

Two-lane admission without outbox reads
---------------------------------------

Remove the startup pending()/capacity query, _pending and _room, and the queued
Job set in _select. Continue querying the authenticated API Job feed with
has_provider_execution_attempt=false. The server evaluates Attempt existence
for that provider regardless of Attempt state, so an open Job whose accepted
START remains recorded is excluded even while its terminal result is queued or
after provider restart. The API's cleanup can delete Attempts as part of cleanup
of logically deleted Jobs; targeted cleanup sets DELETED before removing them.
The reviewed cleanup path therefore does not make that Job eligible for the
OPEN-only feed. This is server-owned exclusion, not a reconstructed
outbox inventory; preserve the original API origin/provider identity. Keep
AttemptClaims.owns_job across both lanes to exclude a Job already selected or
held in this process.
Verify the deployed API's provider identity and Attempt-retention behavior during
integration; the inspected source does not establish uninspected database changes
or the behavior of every deployment.

Keep the existing shared admission lock around selection and use AttemptClaims
as the sole live Job owner. Selection may race with the other lane between
releasing that lock and starting its controller; the SDK controller's
_reserve_start claims the Job synchronously before scheduling START. Handle a
duplicate-Job claim refusal as a no-START selection retry only when the registry
confirms that Job is already owned; surface other ownership failures. Handle
LiveCapacityFull as the existing no-START capacity retry. Do not add another Job
registry or assume selection alone has reserved a claim. Its configured limit
of two owners and 262144 terminal-body bytes reserves at most 131072 bytes per
owner, including owners whose science has stopped but whose exact result is not
yet durably acknowledged. The two loaded runners remain independent; freeing a
runner does not release an unresolved controller's claim or result allowance.

On a full or unavailable outbox, the original controller retains and retries
the exact handoff under existing SDK certainty rules. Pause both lanes' new
admission on the first retryable refusal or unavailable handoff; already admitted
owners may finish and each retains its own bounded result. Resume only after
every blocked original controller reaches its matching durable acceptance or
another existing settled outcome permits release. A lost acknowledgement keeps
the owner and identical handoff; it does not authorize another START or result.
The SDK handoff must bound publication inputs as well as terminal body bytes.

This is a deliberate change from the old pre-start outbox-capacity reservation:
without a read or reservation protocol, even a healthy-looking outbox may become
full immediately after admission. Before the first refusal, up to two local
Attempts can be admitted; the local owner limit bounds their results, but a
later 429 does not prove capacity was reserved or reproduce the previous gate.
If the outbox is already unavailable at startup, its state is not observable
until a submission; the same two-owner bound applies. Refusals pause admission,
and the owner remains responsible for retrying rather than dropping the result.

After a provider restart, local live claims are gone. API Attempt presence still
excludes Jobs whose START was accepted, including Jobs whose result the outbox
already durably accepted; it does not reveal outbox capacity or recover a result
lost before durable acknowledgement. Preserve the existing pre-ack producer-crash
uncertainty and existing START recovery policy; do not claim durable local result
recovery or manufacture another Attempt for an ambiguous outcome. Live outbox
capacity reductions affect future handoff admission; already accepted work stays
owned by the outbox and already admitted local work stays bounded by its owners.

Concrete NMRPeak changes
-------------------------

* nmrpeak_provider/provider_startup.py and provider_config.py currently load a
  selected static binding from a captured bindings.toml. Replace that dependency
  with the issued SDK's provider-owned API identity/settings and the two shared
  grants through existing operational capture. Capture the original credential
  and CA bytes under the existing private ACL and bounded-reader rules. Retain
  API origin/topology for journal_api_authority_id and the existing provider
  identity checks. Do not copy host router settings or introduce another local
  parser or per-provider outbox registration.
* nmrpeak_provider/provider_main.py currently constructs DeliveryClient from
  binding.endpoint. Construct the SDK shared-outbox client and its publication
  handoff from the captured provider API settings and issued credential material.
  Keep separately owned API transports, existing HTTP retirement and the original
  identity lock. The handoff must work after the provider's capture is removed.
* nmrpeak_provider/provider_process.py currently checks delivery.endpoint
  identity, calls pending(), uses provider capacity/items in _room, and requires
  two item slots and 262144 bytes at startup. Replace those reads and checks
  with the local bounded admission and server Job-feed exclusion above. Adapt
  the SDK AttemptController handoff to bind the actual provider identity and
  publication inputs to every submission. Preserve the common HF/CHF gate,
  claims, per-attempt owners, exact commands and retry callbacks.
* nmrpeak_provider/deployment_runtime.py currently renders a private api/api-init
  route and a binding-derived delivery grant. Replace those production projections
  with the issued SDK's two borrowed grants. deployment/provider_deployment.py
  must add external read-only API and outbox mounts and both groups to the provider,
  remove private API service/dependency rendering and capture only client-owned
  identity, trust and publication material. repository_checks/deployment_topology.py
  must admit the two actual grants while preserving scientific topology, runner
  isolation and delivery identity. Operational socket settings do not become
  scientific parameters; retain the existing image/generation derivation rather
  than forcing an old digest after a provider-image rebuild.
* _held_maintenance_api_route currently starts and removes a temporary private
  proxy. Replace it with the shared API grant for journal/archive and retirement
  reads. _run_journal_api_client needs the API group and exact-volume existence
  check. These one-off readers do not need outbox access. Preserve journal and
  identity locks, retained records and invocation cleanup; do not infer a Docker
  client exited merely from an interrupted command. Existing signed API reads
  establish the configured route; no new pre-stop continuity gate is needed.

Lifecycle and retirement
--------------------------

Ordinary down currently discovers old api/api-init mounts via _api_route_volumes,
checks owned resources and uses _run_compose_down with --volumes. Adapt that
maintained path to retire the old owned proxy and unused private API volume after
its clients settle, and retain enough ownership evidence if cleanup fails. Old
roles must remain recognizable by retirement until removed, even after the normal
new service inventory stops rendering them. Exclude both shared volumes from
Compose and custom cleanup; do not weaken guards for owned scientific sessions,
journal, checkpoints or identity-lock storage. Existing outbox deployment owns
retirement of its old proxies and provider-specific delivery intake resources.

An already running archive holds its original lock and route until it settles;
retain unacknowledged work and report incomplete cleanup if a borrower remains.
No old deployment must remain available to protect a cutover. Replace operator
configuration and stop/restart affected services through maintained workflows.
After retirement use a compatible client on the shared route rather than
recreating a private proxy. Historical scientific snapshot housekeeping is
separate from API transport retirement.

Tier 1: first joint deployment
-------------------------------

1. Agree the two SDK grants, push-only submission/publication representation and
   acknowledgement/refusal behavior. The first shared proxy must
   already support live capacity/log/authority control; outbox capacity/retry/log
   controls come from the same host operator file. Neither requires later provider
   changes to restart the proxy.
2. Convert startup, provider handoff and both operational grants, all maintained
   API maintenance paths, topology admission and owned retirement. Update the
   existing focused deployment/runtime, provider process, journal and delivery
   checks for real behavior: two grants and groups, API Job-feed exclusion,
   concurrent two-lane claim exclusion, bounded refusal/unavailability and exact
   handoff retention, lost acknowledgement, restart limits, capacity reduction and
   preservation of shared storage. Keep authored disposable API fixtures owned
   by their test infrastructure. Do not build a new topology or load harness.
3. Obtain the issued SDK through the normal dependency pin/lock and provider image
   build workflow. Keep pyproject.toml, requirements.lock, provider-core release
   records and image-input declarations coherent. Work in the main checkout;
   hosts pull issued source/artifacts and build locally through maintained targets.
4. Bring up proxy and outbox; replace configuration as needed and operate NMRPeak
   through provider/deployment/config, up, down and owned cleanup. Use existing
   signed API/startup checks with the actual client identity, TLS and socket grants.
   Interruptions are acceptable, including while delivery retains pending work.
5. Observe NMRPeak and both runners, its shared mounts/groups and API access,
   functioning outbox handoff and publication where work is available. Account for
   pending/held work; correctly retained retries need not finish. Retire the old
   NMRPeak API proxy and private volume after their clients settle. The shared owner
   retires old delivery API routes/intakes and confirms all four providers and the
   outbox. Local observations do not establish a remote host's deployment.

Alternatives and later work
----------------------------

A single outbox cannot replace the proxy because providers also make direct API
calls. Combining both services couples proxy availability to outbox replacement.
Per-provider proxy processes or intake registration restore lifecycle/configuration
coupling. A pre-signed request cannot sustain publication after a long outage;
transferring the original issued credential and trust inputs to private outbox
storage lets the outbox sign each retry without changing provider identity.

Tier 2: NMRPeak client status/help and small regressions for concrete integration
faults, within the deployed proxy baseline. Tier 3 excludes provider registries,
multi-API orchestration, per-provider router accounting, generic migration tools,
new topology harnesses and speculative load/chaos campaigns. A demonstrated
correctness blocker belongs in Tier 1.
